# 11 — Cross-cutting mechanisms, system-wide coupling & administration

> Knowledge-base chapter. Analysis was read-only and done at `HEAD 41b2ef0` (2026-10-24). The Graphify graph (`graphify-out/`) was built from `c78d1eb4`, which is **119 commits behind HEAD**. Graph-derived numbers are tagged as such, and every fan-in count below was re-measured with `rg` on HEAD.

---

## 1. Scope

This chapter covers the "nervous system" of the ERP: the mechanisms that every business module calls and that turn one business action into many side effects. It also covers the administration console.

- **Notifications**: `notifyUser`, `notifyRoles` and `broadcastNotification`; Web Push; the bell and its polling; per-module menu badges ("pastilles", badges); rewriting old notification links.
- **Audit and events**:
  - `recordAudit` writes to `AuditLog`.
  - The whitelisted "audit → fait métier" (business fact) bridge feeds `BusinessEvent`.
  - The **consequences** of a fact: reconciling tasks, waking missions, satisfying engagements, switching off reminders, waking watches and invalidating hot states.
  - A separate in-memory **domain event bus** (`src/platform/event-bus.ts`).
  - External event ingestion.
- **Activity and adoption**: `ActivityLog` page-view beacons, sessions, and the adoption score.
- **Deletion, trash and cancellation**: the deletion registry (`DELETE_REGISTRY`), the reversible-deletion core (`suppression/coeur.ts`), the trash ("corbeille", `DeletedRecord`), group deletion ("lot", cascade of child records), delegation to the operations director, the pure cancellation rules (`annulations/regles.ts`) and the undo plan (`annulation/plan.ts`).
- **Reference numbering** (`refs.ts`), **custom fields**, the secretariat request catalogue (`admin-requests.ts`), and the **settings layers**: `AppSetting`, `AiSetting`, `AdoptionSetting`, `FeatureFlag`, the missions kill switch, hidden modules and retired modules.
- **Aggregators**: global search, the action centre (`getActionCenter`) that feeds "Mon espace" (personal space) and "Aujourd'hui" (today view), and the per-module menu badges.
- **Coupling map**: the 25+ most depended-upon modules, import cycles, god-files, dead code, the **source-scanning guards** ("cliquets", ratchet tests) and an **impact-analysis playbook**.

## 2. Summary

1. Almost every write goes through `requireUser` (session), then `userCan` (RBAC), a `prisma` write, `recordAudit`, optionally `notifyUser`/`notifyRoles`, and `revalidatePath`. These four library modules have the highest fan-in in the codebase (prisma 885 production files, session 628, rbac 530, audit 236).
2. **`recordAudit` is the hidden event spine.** Every audit line goes through the pure whitelist `faitDepuisAudit`. A match becomes a `BusinessEvent` through `recordEvent`, which then runs **six consequences in parallel, awaited inside the user's request**: task reconciliation, mission wake-up, engagements, reminders, watches and fabric invalidation. A change to `recordAudit`, or to the `module`/`action`/`entityType`/`field` values that callers pass, changes behaviour in missions and tasks far away.
3. All side effects are **best-effort and swallow their errors**: audit, events, notifications, push and the bus. Business writes never fail because of them, so a broken side effect is silent apart from `console.error`.
4. Notifications are only in-app rows plus Web Push. `notifyUser` has **no quiet hours of its own**: the Assistant IA's
   watchers (J12, decision 0024) decide BEFORE notifying (Algiers quiet hours, Fri/Sat, ≤ 5/day, grouping) and notify through
   one door, `prevenir` in `assistant-ia/infra/routines/service.ts` (the module's existing `→ lib/notify` edge, no new debt). **There is no e-mail channel** for standard notifications. The menu badges are computed from the notification **`link` path**, so links are load-bearing.
5. "Suppression définitive" (permanent deletion) is really reversible: the row is hard-deleted and a JSON snapshot goes into `DeletedRecord`. Only `destroyDeletedRecord` (Super Admin) purges. The single-row path is **not transactional**; the "lot" path is.
6. Global search and the action centre are **hand-maintained lists**, not registries. A new module must be added to them by hand. Search visibility must reuse the screen's own list clause (§118.177, enforced by `visibilite-listes.test.ts`).
7. About 80 "cliquet" (ratchet) tests and 232 tests that scan the source tree enforce conventions by reading source code. Examples: the server-action contracts (`contrat.genere.json`, regenerated by `npm run actions:contrat`), the client-bundle guard, the platform boundary debt ceiling, reference numbering, and notification batch replay. Many "safe-looking" refactors trip them.
8. Static import cycles are rare: 2 strongly connected components. God-files: `assistant.ts` (7,309 lines), `ops/catalog.ts` (5,423), `ad-pro-item-actions.ts` (4,454), `labels.ts` (2,284), `rbac.ts` (2,169). At least 10 source modules have no importer at all.

## 4. How it works

### 4.1 Notifications (in-app plus push)

- `notifyUser(input)` (`src/lib/notify.ts:19-28`) [V]:
  - Writes one `Notification` row inside a try/catch that only logs.
  - **Then always awaits** `sendPushToUser`, even when the row write failed.
  - Push options (`tag`, `requireInteraction`) are not stored in the database.
- `notifyRoles(roles, input)` (`notify.ts:84-117`) [V]:
  - Drops unknown role names first. Otherwise Prisma rejects the whole query and nobody is notified; this happened for the HR leave step.
  - Selects active users through `anyRoleFilter` (primary **or** secondary role, `rbac.ts:867`).
  - `createMany`; on failure, replays row by row with `rejouerNotifications`; then pushes to each user.
- `broadcastNotification` (`notify.ts:36-80`) [V]:
  - Audience is ALL, ROLE or USERS. It can set `popup: true`, which shows a full-screen modal until acknowledged.
  - Returns the number of rows **actually written** (§118.51).
- **Batch replay** (`notifications/ecrire.ts:57-76`) [V]: one `create` per row, counts the losses, never throws.
  - The `createMany` deliberately stays in each writer's body. The action-contract derivation reads only one level deep: when the write moved into a helper, 24 actions stopped declaring that they write `notification` (`ecrire.ts:26-42`).
  - A ratchet requires every production `createMany` on notifications to be followed by a `catch` that calls the replay (`ecrire.test.ts`) [V, header].
- **Writers that bypass `notifyUser`** [V]. They write to the bell but **send no push** (no `sendPushToUser` call in the file):
  - `src/lib/tasks/create-core.ts:72`
  - `src/lib/actions/task-actions.ts:240,278,322`
  - `src/modules/rh/actions.ts:679` (salary-advance decision)
  - `src/lib/actions/directive-actions.ts`
  - Only `src/lib/directives/recipients.ts` also pushes.
- **Push** (`src/lib/push.ts:92-122`) [V]:
  1. Exit guard `sortieAutorisee("NOTIFICATION_PUSH", …)`.
  2. VAPID keys come from the environment, otherwise they are generated once and stored in `AppSetting.vapidPublicKey/PrivateKey` (`push.ts:28-51`).
  3. Sends to every `PushSubscription`. A 404/410 response deletes the subscription. Errors never propagate.
- **E-mail is not a notification channel** [V]: `nodemailer` is used only by `src/lib/mail.ts`, which handles user mailboxes, and by the Adam attention door (`src/platform/in-process/courrier/proprietaire.ts:64`).
- **Reading side** [V]:
  - The bell polls `GET /api/notifications/poll` (`route.ts:12-29`) for the unread count plus up to 5 unread pop-ups.
  - `layout.tsx:62-85` loads up to 500 unread notification links per page render and maps each to a module with `moduleForPath(reécriteLienNotification(link))`. This gives `moduleBadges`.
  - `pastillesDesEntrees` (`navigation.ts:141-157`) counts each module once per menu level.
- **Link rewriting** (`notifications/lien-actuel.ts:1-20`) [V]: stored links are never migrated. Old routes are rewritten at display time: list, bell, pop-up, action centre (`action-center.ts:950`) and badges.

### 4.2 Audit, then business fact, then consequences

- `recordAudit(input)` (`src/lib/audit.ts:23-44`) [V]:
  - Writes an `AuditLog` row with the **global** `prisma` client, never a transaction client. Errors are swallowed.
  - Then `await emettreFait(input)`.
  - It is called 892 times across 237 production files [V, rg count].
  - `recordFieldChanges` (`audit.ts:91-133`, used by only 3 files) writes field-level UPDATE rows and emits one fact per changed field.
- `faitDepuisAudit` (`events/from-audit.ts:114-149`) is a **strict whitelist with zero imports** [V]. Rules are checked in this order:
  1. **Action first** (`ACTIONS`, `:91-95`):
     - `UPLOAD` → `DOCUMENT_UPLOADED`
     - `VALIDATE` → `VALIDATION_APPROVED`
     - `REFUSE` → `VALIDATION_REFUSED`
  2. **Creations** (`CREATIONS`, `:98-105`), for these entity types: `CONSULTING_CONTRACT`, `LEGAL_DOCUMENT`, `PCH_TENDER`, `SALE`, `RECRUITMENT_REQUEST`, `MAIL_ENTRY`.
  3. **Status transitions** (`STATUTS`, `:63-88`), for UPDATE with `field`:
     - REGULATORY_PRODUCT.status, any change → `REGULATORY_STATUS_CHANGED`
     - SALE.paymentStatus → PAID, and SALE.deliveryStatus → DELIVERED
     - PCH_TENDER.status
     - TASK.status → DONE
     - EXPENSE_ORDER.status → PAID, and PAYMENT_REQUEST.status → PAID (`PAYMENT_ISSUED`)
  - Anything else returns `null`.
- `recordEvent` (`events/ledger.ts:48-141`) [V] writes `BusinessEvent`. It then runs these consequences with `Promise.allSettled` and **awaits them inside the caller's request** (`:134`). Each consequence has its own `catch`:
  1. `reconcileTasks`: pre-filtered on `EXPECTED_EVENTS` (7 types, `tasks/evidence.ts:46-49`); reads up to 400 open tasks; writes evidence; may set `status: "DONE"` (`ledger.ts:223-235`) **without writing an audit row or a `TASK_COMPLETED` fact**.
  2. `reveillerMissions` (`missions/events/router.ts:49+`): reads **every** `WAITING`/`WAIT_EVENT` mission step on every fact, with no type filter in the database query.
  3. `satisfaireEngagements`.
  4. Dynamic `import("@/lib/assistant/reminders")` then `eteindreRappelsSurEvenement`. It is dynamic so that the messaging stack (and `web-push`) does not load for every fact.
  5. For `MESSAGE_RECEIVED`/`EMAIL_RECEIVED` only: `observerReponseTardive`.
  6. Dynamic `import("@/lib/missions/watch/router")` then `reveillerSurveillances`.
  7. `invaliderEtatsChauds("alertes-executives")`.
- Graphify confirms the chain [V, graph]: `recordAudit → emettreFait → recordEvent → reveillerMissions` (3 hops).
- Direct callers of `recordEvent` in production [V]:
  - `audit.ts`
  - `workflow/engine.ts`
  - `actions/consulting-actions.ts`
  - `google/gmail/ingest.ts`
  - `events/messaging-events.ts`
  - `platform/in-process/events/ingestion.ts` (external webhooks, reached through `/api/events/inbound/[source]`)
  - `platform/in-process/missions/acceptance.ts`

### 4.3 The in-memory domain bus (a separate, lightly used channel)

- `publish`/`subscribe` (`platform/event-bus.ts:58-101`) [V]:
  - In-process and not persisted. Keeps the last 500 events for replay.
  - Each handler is isolated in a try/catch.
  - The header admits that with several server instances, each instance sees only its own events.
- `emit()` (`platform/events.ts:76-97`) only accepts the 17 `DOMAIN_EVENTS` types and never throws.
- **Adoption is minimal** [V]: only 3 of the 17 types are emitted in production:
  - `regulatory.owner-changed` (`regulatory-actions.ts:825`)
  - `hr.employee-added` (`modules/rh/actions.ts:98`)
  - `mail.sent` (`comms/outbound.ts:515`)
- The only subscriber is `assistant/platform/change-feed.ts:78`. Treat the bus as an Adam-cache accelerator, not as business plumbing.

### 4.4 Activity, sessions, adoption

- **Page views.** `POST /api/activity` (`api/activity/route.ts:10-63`) [V]:
  - Writes one `ActivityLog` row with `type: "PAGE_VIEW"` and `module` = **the first URL segment**.
  - Adds device, OS and browser, IP, and country/city from the `UserSession`; GPS coordinates take precedence when the browser consented.
  - Fails silently with HTTP 204.
- **Sessions** are `UserSession` rows (`revokedAt`, `expiresAt`). They are revoked in `access-actions.ts:232,305,329,365`, `auth-actions.ts:76` and `modules/rh/infra/depart.ts:52` [V].
- **Adoption** (`src/lib/adoption.ts`) [V]:
  - 30-day window. 8 weights (`DEFAULT_ADOPTION_SETTINGS`, `:76-82`): regularity, time, breadth, diversity, durable work, interaction, recency, cycle.
  - Overridable through the `AdoptionSetting` row (`:112-127`). Super Admins are excluded (`:226`).
  - "Breadth" takes the **UNION of `ActivityLog.module` (URL segment) and `AuditLog.module` (free text)** (`:232-240`).
  - The personal badge is cached for 12 hours (`BADGE_TTL_MS`, `:29`) and loaded in `layout.tsx:66`.

### 4.5 Deletion, trash, cancellation

1. **Rights are checked by the caller.**
   - `superAdminDelete` and `deleteOwnRecord` (`admin-delete-actions.ts:64,94`) check the right, and so do module actions such as `deleteEvent`.
   - Delegation to the operations director goes through `suppressionPermise`/`corbeillePermise` (`suppression/delegation.ts:35-57`). It applies to the kinds in `MODULE_DU_TYPE` when the person holds the module's `DELETE` right. **Permanent destruction stays reserved to the Super Admin.**
2. **The core, `supprimerReversible(kind, id, actor, summary)`** (`suppression/coeur.ts:36-104`) [V]:
   1. `spec.refuse(id)` gives a named reason for a refusal.
   2. `spec.describe(id)` returns `null` for "introuvable" (not found).
   3. If `spec.lot`, go to `supprimerAvecBranches`.
   4. Otherwise, in order:
      - snapshot the head row;
      - snapshot and delete polymorphic `Document`/`Comment` rows;
      - `spec.remove(id)`, which cascades in the database;
      - on failure, re-create the documents and comments;
      - `deletedRecord.create`, then `recordAudit(DELETE)`, then `revalidatePath(spec.redirect)`.
   - **These are separate statements with no transaction.** If `deletedRecord.create` fails after `remove`, the row is gone with no snapshot [V, by reading; no guard seen].
3. **The "lot" path** (`coeur.ts:111-140`) [V]:
   - `inventorier` re-reads the child records ("branches"). Any blocking items refuse the deletion.
   - `supprimerLot` deletes everything and writes `DeletedRecord` (with a `lot` JSON) **in one transaction**.
4. **Restore** [V]:
   - `restoreDeletedRecord` (`admin-delete-actions.ts:145-205`) re-creates the head row, its documents and comments, or the whole lot through `restaurerLotDeLaCorbeille` (`coeur.ts:146-164`, which refuses if any part already exists).
   - It calls `spec.restored`, for example to re-debit leave balances.
   - Files stay in storage until `destroyDeletedRecord` (`:209`) purges them.
5. **Other mechanisms** [V]:
   - The Drive has its **own** soft-delete flag (`DriveNode.isTrashed`).
   - Messages use `deletedAt`, shown as "message supprimé".
   - `AdministrativeRequest` uses `deletedAt` (`action-center.ts:216`).
   - `DeletedRecord` itself has `restoredAt` and `purgedAt` (`schema.prisma:9296-9316`).
   - Trash screens: `/admin/corbeille` (Super Admin), `/corbeille` (operations director; navigation gate `corbeilleOps`, `labels.ts:2220`), `/demandes/corbeille`.
6. **Cancellation is not deletion** [V]:
   - `annulations/regles.ts` holds pure functions that return a refusal reason or `null`. The UI and the action read the same rule (§118.83).
   - `annulation/plan.ts` is Adam's undo planner: undo a change only if the field still holds the written value, and undo in reverse order (`plan.ts:14-30`).

### 4.6 References, custom fields, secretariat catalogue, settings layers

- **References** (`refs.ts:13-82`) [V]:
  - `buildRef` computes max + 1 (resistant to gaps). `createWithRetry` retries up to 6 times on P2002. `enSerie(serie, fn)` is an in-process FIFO per series.
  - Measured: 10 parallel purchase orders broke `createWithRetry` alone (§118.148). The app runs in a single process (`render.yaml`).
  - Usage: `buildRef` in 32 files, `createWithRetry` in 25, `enSerie` in 26 [V].
  - `refs-filet.test.ts` lists 9 files known to have no safety net as named **debt** (`DETTE`). The list can only shrink.
- **Custom fields** [V]:
  - `CustomFieldDef(entityType, key, type, required…)` (`schema.prisma:5485`); values live in each record's `custom` JSON column.
  - 18 entity types are enabled (`custom-fields.ts:5-9`), but **`CustomFieldsCard` is rendered on only 3 pages**: `rh/[id]`, `regulatory/[id]`, `drive/[id]`.
  - Client components must import the pure `custom-field-values.ts`, never `custom-fields.ts` (`custom-field-values.ts:1-6`).
- **`admin-requests.ts`** [V]: `REQUEST_TYPES` has 8 entries. `HR_SIMPLE` and `DRIVER` are closed to new requests, but their enum values and labels are kept so that old rows still display (`:6-20`).
- **Settings layers** [V]:
  - `AppSetting` row `"global"` (150 schema lines). `getAppSettings` is memoised per request with React `cache`, and returns `DEFAULT_APP_SETTINGS` when the row is missing **or on any database error** (`settings.ts:146-183`). It holds:
    - upload limits;
    - budget mode;
    - thresholds for Ad & Pro (`adProDgThreshold`) and purchase orders (BC);
    - Drive capacity and quota;
    - role and user lists for regulatory, pipeline, directives, org chart, field reports and promo messages;
    - `hiddenModules`, `generalMeansDepartmentId`;
    - `aiExternalActionsDisabled`, the emergency stop for the AI's external actions.
  - `AiSetting` (`ai-settings.ts:137-157`): a master switch and per-feature toggles, with a global AI kill switch (`iaCoupeeGlobalement`).
  - `AdoptionSetting`: adoption weights and thresholds.
  - `FeatureFlag` (`features.ts`): TEST (test-mode users only) → PROD → OFF, auto-created on first use.
  - Missions kill switch: `interrupteurs/missions.ts`.
  - **Hidden** modules (`modules-visibility.ts`): a setting. The Super Admin still sees them; ADMIN can never be hidden. Enforced in `requireModule` (`session.ts:250-255`), **not** in `userCan`, so server actions of a hidden module still work.
  - **Retired** modules (`modules-retired.ts:47`): `SALES`, `LOGISTICS`, `BUSINESS_DEVELOPMENT`. A code decision, removed in `getAccess`, so `userCan` returns false everywhere.

### 4.7 Global search and the action centre

- **Search**:
  - Entry points: `GET /api/search?q=` (`api/search/route.ts`, 6 results per group) and `/search`. Both call `globalSearch(user, q)` (`queries/search.ts:44+`) [V].
  - Algorithm: at most 6 terms, combined as AND of terms × OR of fields, case-insensitive `contains`.
  - **23 families** are queried in one `Promise.all`. Each is gated by `userCan(user, MODULE, "VIEW")`, and each **must reuse the list clause of its own screen** (`regulatoryVisibleWhere`, `visibilite-listes.ts`, `accessibleDocumentWhere`…), per §118.177 (`search.ts:36-43`).
- **Action centre**. `getActionCenter(user)` (`queries/action-center.ts:138-969`) [V] is a numbered **hand-written** sequence of blocks:
  1. tasks;
  2. validations where it is my turn (2b: leave, purchases, tour plans, absentee training, Ad & Pro missions; 2c: Ad & Pro sent back for correction);
  3. secretariat requests assigned to me;
  4. payments for the accountant;
  5. my regulatory dossiers;
  6. 6a–6h: Ad & Pro arbitration, congresses, medical info, promo material, requested documents, directives, support, dossiers, stock-count requests;
  7. unread notifications.
  - Blocks run mostly **sequentially**. Each item carries `objet = "TYPE:id"`, which `dedoublonner` uses to show an object only once.
  - Consumers [V]: `mon-espace/page.tsx` (through `aujourdhui-espace.ts`), `chief-of-staff/page.tsx`, `queries/today.ts`, `espace/aujourdhui.ts`, Adam tools (`power-tools.ts`, `executive-brief-tools.ts`, `what-if.ts`) and `platform/in-process/inbox/compose.ts`.

### 4.8 Scheduler (where many notifications come from)

- `src/lib/scheduled.ts` arms a `setInterval` heartbeat (`TICK_MS`, at least 15 seconds, default 60) **when the module is first loaded** (`:79-92`). The main importer is `/api/messaging/sync` (`route.ts:6,17`), which also calls `void runScheduledJobs()` on every poll.
- `runScheduledJobs` is debounced to once per minute per process (`:95-100`). It runs about 30 jobs in sequence: meeting reminders, payroll notifications, leave accrual, regulatory jobs, sweeps, mission sweeps…
- Kill switch: `SCHEDULER_DISABLED=1`. The scheduler does not run under Vitest or during the build [V].

## 5. House style (conventions to follow)

1. **Write order inside a server action**:
   1. `requireUser()`, or `requireModule()` for pages.
   2. A literal `userCan(user, "MODULE", "ACTION")`.
   3. Parse with `fdStr`/`fdNum`/`fdDate`.
   4. Prisma write; conditional `updateMany({ where: { id, status: "PENDING" } })` for "un geste à la fois" (one gesture at a time).
   5. `notifyUser`/`notifyRoles`.
   6. `recordAudit({ actorId, action, module, entityType, entityId, field?, newValue?, summary })`.
   7. `revalidatePath(...)`.
   8. Return an `ActionResult` (`actions/types.ts:4`).
   - The **literal forms matter**: `contrat.ts` derives each action's contract with regexes on `recordAudit({ module: "…" })`, `userCan(x, "MOD", "ACT")` and `fdStr(formData, "key")` (`contrat.ts:437,468,617-626,775`). A wrapped or indirect call degrades the contract to "illisible" (unreadable) or drops a written table.
2. **Side effects never fail the business write.** Wrap them in try/catch and log. Emit **after** the write is committed (`event-bus.ts:20-22`, `events.ts:72-74`).
3. **Notifications**:
   - Go through `notify.ts`. Bulk writers must keep `createMany` in their own body and `catch` it with `rejouerNotifications`.
   - Always set `link` to the **current** route: it drives the menu badges.
   - When a route moves, add a rewrite rule to `lien-actuel.ts`; never migrate stored rows.
4. **Facts**:
   - Make a status change visible to missions and tasks by auditing it **with `field`, `oldValue` and `newValue`** (or with `recordFieldChanges`), not with a summary alone.
   - Add a new fact type to `from-audit.ts`, which is the whitelist, **and** to `events/catalogue.ts`.
5. **Pure modules first.**
   - Rules shared between server and client (annulation rules, `custom-field-values`, `lien-actuel`, `espace/aujourdhui`, `modules-retired`, `from-audit`, `joignabilite`) live in files with **no imports**. The server re-exports them.
   - Enforced by `client-bundle-guard.test.ts`. Its Node-only list covers `fs`, `zlib`, `child_process`… plus `web-push`, `nodemailer`, `imapflow`, `sharp`, `mupdf`, `pdfkit`, `pdf-parse`, `yauzl`, `@mastra/core` (`:28,41-43`).
6. **Deletion**:
   - Register the kind in `DELETE_REGISTRY` with `describe`/`remove` and, as needed, `refuse`/`lot`/`restored`/`reserve`/`creatorOf`/`searchFields`.
   - Never call `prisma.X.delete` directly from a user action (§118.162 history: `deleteEvent`).
   - Cancellation of requests goes through `annulations/regles.ts`.
7. **Numbering**: `createWithRetry(() => enSerie("SERIE", () => …buildRef(…)))`. Recompute the reference **inside** the retried function.
8. **Visibility**: lists, search, action centre and entity access all reuse **one clause per family** (`visibilite-listes.ts`, `rbac.ts scope*`). Never recompose a scope locally (§118.5, §118.71, §118.177).
9. **API routes that write** use `getCurrentUserPourEcrire()`, never `getCurrentUser()` (`session.ts:263-271`; §118.184 Vue exacte, the Super Admin's view-as-another-user mode).
10. **Migrations**: hand-written idempotent SQL (`ADD VALUE IF NOT EXISTS`, `CREATE TABLE IF NOT EXISTS`), applied with `npm run db:deploy` (`prisma migrate deploy`).

## 6. End-to-end flows traced

### Flow A — A validator approves a step (`decideValidation`, `src/lib/actions/validation-actions.ts:339-565`) [V]

1. `requireUser()` (`:340`), then parse with `fdStr` (`:341-343`).
   - `motifExige` refuses REJECTED or CHANGES_REQUESTED without a reason (`:352`).
   - The `reason === null` form is written so that the contract derivation does not mark the field mandatory.
2. Load the step and its request. `droitSurLEtape` accepts the validator **or** their stand-in during leave ("intérim"), never on one's own request (`:363-367`). Status and turn checks follow (`:368-376`).
3. `prisma.$transaction` (`:383-416`):
   - `SELECT … FOR UPDATE` on the request.
   - Re-read the steps.
   - Conditional `validationStep.updateMany({ where: { id, status: "PENDING" } })`.
   - Compute the outcome with the pure `issueDeLaDecision`; update the request; set the other steps to SKIPPED when one validator suffices.
4. After commit:
   - `notifyValidator(next)` (`:419`).
   - `notifyUser(requester)` with a final or partial message and `link: /validations/{id}` (`:444-471`). This writes the `Notification` row, then `sendPushToUser`, which passes through the exit guard.
5. `recordAudit({ action: decision === "REJECTED" ? "REFUSE" : "VALIDATE", module: "Validations", entityType: "VALIDATION_REQUEST", field: "decision", newValue: decision })` (`:473-479`). This writes `AuditLog`, then `faitDepuisAudit` (the action rule wins), then `VALIDATION_APPROVED`/`VALIDATION_REFUSED`.
6. `recordEvent` writes `BusinessEvent`. The 6-way consequences are awaited **inside this request**:
   - `reconcileTasks` exits early, because `VALIDATION_*` is not in `EXPECTED_EVENTS`.
   - `reveillerMissions` scans every waiting `WAIT_EVENT` step.
   - Engagements, reminders, watches and the fabric invalidation also run.
7. For an approved attached document with an amount, an expense order is emitted, with a double read against concurrent cancellation (`:480-540`).
8. `revalidatePath` runs on `/validations`, `/admin/validations`, `/mon-travail` (a redirect stub), the linked object's paths, and so on (`:547-565`).
9. Read side for the requester:
   - The bell poll counts +1.
   - `layout.tsx` maps `/validations/...` to the VALIDATIONS module, which gets a badge.
   - On the validator's side, `getActionCenter` block 2 drops the item, because `actionable` is now false.

**Defect found** [V for the mapping, U for the impact]:
- `CHANGES_REQUESTED` is audited as `action: "VALIDATE"` (`:474`), and `ACTIONS.VALIDATE` maps to **`VALIDATION_APPROVED`** (`from-audit.ts:93`). Non-final partial approvals also emit `VALIDATION_APPROVED`.
- `VALIDATION_APPROVED` is in the planner catalogue (`events/catalogue.ts:30`). A mission waiting for "validation approved" on that request could therefore be woken by a "send back for correction".

### Flow B — The Super Admin deletes an expense order and restores it [V]

1. `superAdminDelete(formData)` (`admin-delete-actions.ts:64-77`) checks Super Admin or operations director, then calls `supprimerReversible("EXPENSE_ORDER", id, …)`.
2. In `coeur.ts`: there is no `refuse`; `describe` returns "REF — label"; it is not a lot. Then: snapshot of `expenseOrder`; documents and comments for `EXPENSE_ORDER` are snapshotted and deleted; `expenseOrder.delete`; `DeletedRecord` is created; `recordAudit(DELETE, module "Finances")`; `revalidatePath("/finances/paiements-a-faire")`.
3. A `DELETE` audit line matches **no** fact rule, so no `BusinessEvent` is written.
4. `restoreDeletedRecord` checks `corbeillePermise` and re-creates the row from the JSON payload, then documents and comments with `skipDuplicates`. It writes `recordAudit` and revalidates `/admin/corbeille` and `/corbeille` (`admin-delete-actions.ts:145-205`).

### Flow C — A page view feeds the adoption score [V]

1. The client beacon calls `POST /api/activity`, which writes an `ActivityLog` row with `module="finances"` (URL segment).
2. `getAdoptionScores` takes the UNION with `AuditLog.module="Finances"`, then counts distinct `(uid, module)` pairs for "breadth".
3. The case and vocabulary mismatch inflates breadth (see §8.7).

## 8. Invariants, gotchas, doctrine

1. **Side effects never fail the write; errors are swallowed.**
   - Audit (`audit.ts:19-22,39-41`), ledger (`ledger.ts:17-23`, "le SEUL endroit … où avaler une erreur est le bon choix", the only place where swallowing an error is right), bus (`event-bus.ts:14-19`), notifications (`ecrire.ts:54-55`).
   - **Gotcha:** a broken side effect only shows up as `console.error`. When a "the notification didn't arrive" bug comes in (§118.200 in `docs/claude-md/08-…-p05.md:167`), read the server logs.
2. **Audit runs outside the transaction.** `recordAudit` uses the global client, so an audit line written inside a `$transaction` callback survives a rollback, and a later-failing tx leaves an orphan fact [U: no call site inside a tx was checked exhaustively]. The convention is to audit after commit (`validation-actions.ts:473`).
3. **Fact consequences are synchronous for the user.** Every audited status change waits for 6 parallel queries, including an unfiltered scan of all waiting mission steps (`router.ts:51-61`). The latency grows with the number of active missions [V code, U production impact].
4. **The audit vocabulary is load-bearing.** `module` is free text: 230 distinct literals, with duplicates such as "Administration"/"ADMIN", "RH"/"Ressources humaines", "Regulatory"/"REGULATORY", "Finances"/"FINANCES" [V, rg]. It feeds:
   - `BusinessEvent.sourceDomain`;
   - adoption "breadth" and "diversity" (§4.4);
   - the action contracts (`contrat.ts:97`, "434 actions le déclarent", 434 actions declare it).
   - `action`/`entityType`/`field`/`newValue` drive `faitDepuisAudit`: renaming an entity type or status field silently stops the facts.
5. **Notification links are routing.** Badges come from `moduleForPath(link)`. When a route is deleted or renamed, add a `lien-actuel.ts` rule, or the bell and badges send users to 404 pages or to the wrong module.
6. **Writing notifications directly skips push.** Use `notifyUser` unless push must be suppressed on purpose (§4.1).
7. **`DEFAULT_APP_SETTINGS` must match the SQL `@default` values** (`settings.ts:4-11`, §118.138). `getAppSettings` returns the defaults on **any** error, so a broken column silently resets every threshold (for example `bcValidationThreshold: 0`, which routes every purchase order through a validation centre) [V code].
8. **Hidden ≠ retired ≠ denied.**
   - Hidden is enforced only in `requireModule` (pages).
   - Retired is enforced in `getAccess`, so it applies everywhere.
   - Denied comes from RBAC.
   - The ADMIN module cannot be hidden (`modules-visibility.ts:28`).
9. **Reversible deletion, but:**
   - The non-lot path is not atomic (§4.5).
   - What cascades in the database is not restored unless `lot: true`; `reserve` says so in the confirmation sentence (`admin-delete-registry.ts:73-84`).
   - Restore re-creates rows with their original IDs and fails when a reference has been reused since (`coeur.ts:160`).
10. **Numbering is single-process.** `enSerie` only serialises inside one process. Scripts or a second instance rely on `createWithRetry` (`refs.ts:61-64`).
11. **The bus is per process.** Never use it for correctness (`event-bus.ts:25-32`). `BusinessEvent` is the canonical register (§118.5: "Ne rien recréer… `BusinessEvent` le registre canonique", do not rebuild what exists).
12. **The exit guard.** Under `NODE_ENV=test`, `VITEST`, `PLAYWRIGHT*` or benches, push, e-mail and similar exits are recorded but never sent (`sortie/garde.ts:126-139`); `ADAM_SORTIE_AUTORISEE=1` overrides it.
13. **One clause per family** (§118.177, §118.5, §118.71). Search, the action centre and entity access must not re-implement a list's visibility.
14. **Lint before build** (CLAUDE.md, §118.155). Render runs `next lint && next build`, so a single lint error blocks deployment.
